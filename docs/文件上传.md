# 文件上传



## 设计思路

文件传输必须满足以下几个条件

* 限制文件大小(不超过4G)

* 长连接传输(效率高，支持大文件)

  > 文件传输不允许任何数据丢失，并且需要保证数据包到达顺序，而且TCP有流量控制和拥塞控制，更适合文件传输

* 客户端和服务器都知道传输进度，以保证支持断点续传(后续实现)



先实现单线程处理版本，再实现多线程的



## 客户端

客户端由`TcpClient`来进行数据的发送

```cpp
//发送数据槽函数
void TcpClient::slot_send_msg(quint16 id, QByteArray body)
{
    //如果连接异常则直接返回
    if(_socket->state() != QAbstractSocket::ConnectedState){
        emit sig_net_error(QString("断开连接无法发送"));
        return;
    }

    //获取body的长度
    quint32 bodyLength = body.size();

    //创建字节数组
    QByteArray data;
    //绑定字节数组
    QDataStream stream(&data, QIODevice::WriteOnly);
    //设置大端模式
    stream.setByteOrder(QDataStream::BigEndian);
    //写入ID
    stream << id;
    //写入长度
    stream << bodyLength;
    //写入包体
    data.append(body);

    //发送消息
     _socket->write(data);
}
```

发送格式`id + bodylength + 文件流数据`

bodylength是4个字节，所以文件最大是4G

由其他地方发送信号实现数据发送

```
 //连接 发送数据信号和槽函数
 connect(this, &TcpClient::sig_send_msg, this, &TcpClient::slot_send_msg);
```

客户端选择文件后，点击发送会把文件切分成固定大小的报文发送

```cpp
void MainWindow::on_uploadButton_clicked()
{
    // 设置按钮不可点
    ui->uploadButton->setEnabled(false);
    QFile file(_file_path);
    if(!file.open(QIODevice::ReadOnly)){
        qWarning() << "Could not open file:" << file.errorString();
        return;
    }
    
    QFileInfo fileInfo(_file_path); // 用完整路径构造
    int total_size = fileInfo.size();
    int last_seq = 0;
    // 计算分块大小
    if(total_size % MAX_FILE_LEN){
        last_seq = total_size  / MAX_FILE_LEN + 1;
    }else{
        last_seq = total_size / MAX_FILE_LEN;
    }
    
    // 读取文件内容进行发送
    QByteArray buffer;
    int seq = 0;
    while(!file.atEnd()){
        // 每次读取2048字节，分块传输
        buffer = file.read(MAX_FILE_LEN);
        QJsonObject jsonObj;
        // 将文件内容转换位Base64编码
        QString base64Data = buffer.toBase64();
        seq++;
        jsonObj["md5"] = _file_md5;
        jsonObj["name"] = fileInfo.fileName(); //提取出文件名
        jsonObj["seq"] = seq; // 报文序列号
        jsonObj["trans_size"] = buffer.size() + (seq-1)*MAX_FILE_LEN; //已经传输的大小
        jsonObj["total_size"] = total_size;
        if(buffer.size() < MAX_FILE_LEN){
            jsonObj["last"] = 1;
        }else{
            jsonObj["last"] = 0;
        }
        jsonObj["data"] = base64Data;
        jsonObj["last_seq"] = last_seq;
        QJsonDocument doc(jsonObj);
        auto send_data = doc.toJson();
        emit TcpClient::GetInstance()->sig_send_msg(ID_UPLOAD_FILE_REQ, send_data);
    }
}
```

```cpp
void LogicSystem::HandleUploadFile(std::shared_ptr<CSession> session, const short &msg_id, const std::string &msg_data)
{
    Json::CharReaderBuilder reader;
    Json::Value root;
    std::istringstream ss(msg_data);
    std::string errs;
    bool parse_success = Json::parseFromStream(reader, ss, &root, &errs);
    if (!parse_success) {
        std::cout << "Failed to parse JSON data" << std::endl;
        std::cout << errs << std::endl;
        return;
    }

    Json::Value rtvalue;
    Defer defer([this, session, &rtvalue]() {
        std::string return_str = rtvalue.toStyledString();
        session->Send(return_str, ID_UPLOAD_FILE_RSP);
    });

    std::string data = root["data"].asString();
    // 客户端上传的是 Base64 文本，保存前必须还原为原始二进制字节。
    std::string decoded_data;
    if (!Base64Decode(data, decoded_data)) {
        std::cout << "Failed to decode Base64 data" << std::endl;
        rtvalue["error"] = ErrorCodes::Error_Json;
        return;
    }

    auto seq = root["seq"].asInt();
    auto name = root["name"].asString();
    auto total_size = root["total_size"].asInt();
    auto trans_size = root["trans_size"].asInt();
    auto file_path = ConfigMgr::Inst().GetFilePath();
    // JSON 中的中文文件名为 UTF-8，u8path 可避免 Windows 按本地代码页解释而乱码。
    // filename() 只保留名称，防止客户端传入 "../" 等路径越界写文件。
    auto file_name = std::filesystem::u8path(name).filename();
    if (file_name.empty()) {
        std::cout << "Invalid file name" << std::endl;
        rtvalue["error"] = ErrorCodes::Error_Json;
        return;
    }
    auto file_path_str = file_path / file_name;
    std::cout << "file_path: " << file_path_str << std::endl;
    std::ofstream outfile;
    if(seq == 1){
        // 第一个包需要创建
        // 打开文件，如果存在则清空，不存在则创建
        outfile.open(file_path_str, std::ios::binary | std::ios::trunc);
    }else{
        // 保存为文件
        outfile.open(file_path_str, std::ios::binary | std::ios::app);
    }
    if(!outfile){
        std::cout << "Failed to open file" << std::endl;
        return;
    }
    outfile.write(decoded_data.data(), decoded_data.size());
    if(!outfile){
        std::cout << "Failed to write file" << std::endl;
        return;
    }
    outfile.close();
    std::cout << "Write file success" << name << std::endl;

    rtvalue["error"] = ErrorCodes::Success;
    rtvalue["seq"] = seq;
    rtvalue["name"] = name;
    rtvalue["total_size"] = total_size;
    rtvalue["trans_size"] = trans_size;
    }
```

## 多线程逻辑服务器

多线程逻辑服务器主要是为了缓解单线程接收数据造成的瓶颈，因为单线程接收数据，就会影响其他线程接收数据，所以考虑引入线程池处理



划分多线程的几种思路

* 按照任务划分，将不同的任务投递给不同的线程

  也就是不要让IO线程既收包，又解码，又写文件，可以分为

  * 网络线程：接收tcp数据，拆包

  * 解析线程：解析json
  * 文件线程：创建目录，写入文件分片
  * 网络线程：文件写成功后发送上传回包

  这一磁盘写入慢时，不会阻塞其他客户端继续收包

* 按照线程数轮询处理

  也就是现在 `AsioIOServicePool`的思路

* 按照递归的方式划分

  递归：也就是大任务拆成小任务

  例如一个大文件范围：

  ```
    [0, 文件末尾]
            ↓
    拆成 [0, mid] 和 [mid + 1, 文件末尾]
            ↓
    继续拆分，直到每块不超过设定大小
            ↓
    每一块成为一个可投递任务
  ```

现在客户端已经按照2048字节上传分片，不需要服务器再拆，服务器可以直接将每个收到的分片作为一个任务投递即可，所以考虑第二种，服务器通过`iocontext`池接收数据，将接收的数据投递到线程池

关键在于，同一文件的分片要保证顺序写入

有几种处理思路



### 按照文件划分

```
  文件 A 的所有分片 → 固定文件线程 0
  文件 B 的所有分片 → 固定文件线程 1
  文件 C 的所有分片 → 固定文件线程 2
```

用文件唯一标识计算对应的固定线程，比如MD5

在固定现在内部按队列顺序写入，从而可以安全的使用`std:ios::app`

还需要保留`seq`校验，因为分片可能重传，跨连接上传

```
  struct UploadState {
      int next_seq = 1;                     // 下一个允许写入的分片
      std::map<int, FileChunk> pending;     // 先到但尚不能写的分片
      std::mutex mutex;
  };
```

写入逻辑

```cpp
 void HandleChunk(const FileChunk& chunk)
  {
      std::lock_guard<std::mutex> lock(state.mutex);

      if (chunk.seq < state.next_seq) {
          return; // 已写过：重传包，忽略或直接回成功
      }

      state.pending[chunk.seq] = chunk;

      // 只有连续分片才允许追加写入
      while (state.pending.count(state.next_seq)) {
          auto& current = state.pending[state.next_seq];
          AppendToFile(current.data);

          state.pending.erase(state.next_seq);
          ++state.next_seq;
      }
  }
```

但是呢，这一有个弊端，如果文件很大，需要等待重组完成才能组合成一个统一的包，这个时间很长

当然也可以缓存这些数据，每次收到后排序组合，但是比较麻烦



### 按照客户端划分

另一种思路，按照不同的客户端区分

```
  客户端 A 的所有请求 → 工作线程 0
  客户端 B 的所有请求 → 工作线程 1
  客户端 C 的所有请求 → 工作线程 2
```

只要同一客户端的任务在同一条单消费者队列中执行，TCP接收顺序就是业务处理顺序，分片就可以继续使用`std::ios::app`追加写入

可以使用`session_id`计算线程索引

```
 std::size_t GetWorkerIndex(const std::string& session_id)
  {
      return std::hash<std::string>{}(session_id) % _workers.size();
  }
```

投递的时候

```
auto index = GetWorkerIndex(session->GetSessionId());

_workers[index]->Post([session, msg_data]() {
	HandleUploadFile(session, msg_data);
});
```

这样，同一连接发送的seq =  1, 2, 3 ... 会进入同一工作线程

一个客户端的多个请求也会保持先后顺序，不同客户端可以并行上传

当前`CServer`已经是这样的写法

```
  void CServer::StartAccept() {
      auto& io_context = AsioIOServicePool::GetInstance()->GetIOService();

      auto new_session =
          std::make_shared<CSession>(io_context, this);

      _acceptor.async_accept(new_session->GetSocket(), ...);
  }
```

CSession 的 socket 在创建时就绑定了本次轮询得到的 io_context

```
  客户端 A 建连 → 分配 IO 线程 0
  客户端 A 的分片 1、2、3 → 都由线程 0 的 CSession 处理

  客户端 B 建连 → 分配 IO 线程 1
  客户端 B 的分片 1、2、3 → 都由线程 1 的 CSession 处理
```



但是，当前逻辑处理是单线程，所有客户端业务串行执行

```
  客户端 A 上传分片 1
  客户端 B 上传分片 1
  客户端 A 上传分片 2
```

我们完成一下多线程逻辑处理，一个客户端用一个`logic_worker`，于是

* 同一个客户端仍按顺序处理
* 不同客户端可以并行写不同文件
* IO线程不被磁盘写入阻塞



### 处理逻辑

我们先在逻辑层这里做一下解耦合，将logic线程扩充为多个，按照`sessionid`将不同的客户端连接分配给不同的线程处理

让`LogicSystem`作为业务调度中心

```
创建和管理多个LogicWorker
客户端连接建立时候，为该客户端分配一个LogicWorker
收到CSession投递的LogicNode后，根据客户但所属Worker转发任务
连接断开后，删除session_id -> worker 的映射
```

这样同一客户端永远由同一个LogicWorker顺序执行，不同客户端会被轮询分到不同的worker并行处理

```

    std::unordered_map<std::string, std::size_t> _session_worker_map; // session到worker的映射
    std::atomic<std::size_t> _next_worker; // 下一个worker，轮询处理
};
```

## 断点续传



### 方案

断点续传通过借助MD5(或更常见的SHA-256)来确认已传部分和最终文件是否正确

* 断点续传：上传/下载中断后，从已完成的位置继续传，核心是记录偏移量，分片编号和已完成分片

* MD5：文件内容的摘要/指纹，用于识别内容和校验完整性

  > MD5是一种哈希算法，全程 Message Digest Algorithm5 消息摘要算法5
  >
  > 它会把任意大小的数据，例如一个文件，一段文本，计算成固定长度的32位十六进制字符串
  >
  > 常用于文件完整性校验，文件去重，上传任务标识

* SHA-256，和MD5类似，不过它是生成64位十六进制字符串



常见组合方式

* 秒传/去重

  客户端先计算整个文件的MD5并询问服务端是否已有该文件，已有无需上传，没有开始分片上传

* 续传定位

  客户端带上MD5作为上传任务标识，请求服务端查询已上传的分片或偏移量，然后仅补传缺失部分

* 完整性校验

  上传完成后，服务端计算合并后文件的MD5，与客户端提供的MD5比较

* 分片校验

  也可每个分片带一个MD5，服务器逐片验证，避免某个分片传输损坏后仍被合并



### 具体实现

本项目的断点续传不是在 TCP 层“记住上一次连接”，而是把**上传任务**持久化到磁盘。TCP
断开后会话会消失；但客户端用同一份文件重新计算出相同的 `upload_id`，服务端就能从该任务
目录中的临时文件大小恢复进度。

#### 改造前：只能顺序追加，不能可靠续传

原来的客户端在点击“开始上传”后，马上用 `while (!file.atEnd())` 读取完整文件，并一次性把
所有分片发送出去。每个分片带有：

```json
{
  "md5": "...",
  "name": "报告.docx",
  "seq": 1,
  "trans_size": 2048,
  "total_size": 10240,
  "data": "Base64..."
}
```

原来的服务端逻辑是：`seq == 1` 时以 `std::ios::trunc` 创建文件，其余分片以
`std::ios::app` 追加到 `uploads/文件名`。

```cpp
if (seq == 1) {
    outfile.open(file_path / file_name, std::ios::binary | std::ios::trunc);
} else {
    outfile.open(file_path / file_name, std::ios::binary | std::ios::app);
}
```

这适合“一条连接、从头到尾、不发生异常”的演示，但有三个问题：

1. 断线后客户端不知道服务端实际保存到哪里；若重新从 `seq = 1` 发送，会把临时文件截断。
2. 如果客户端猜测从中间继续发送，服务端只会追加，重复包会重复写入，跳包会造成文件缺洞。
3. 所有人都写 `uploads/文件名`，两个客户端上传同名文件会互相覆盖。

因此，不能只靠 `seq` 和 `app` 实现断点续传；需要由服务端确认一个**连续、已落盘的字节偏移量**。

#### 1. 用 upload_id 标识一项上传任务

客户端在选择文件时已经计算 MD5。开始上传时使用以下规则生成稳定的任务 ID：

```cpp
upload_id = md5 + "_" + file_size + "_" + MAX_FILE_LEN;
```

例如：

```text
9e107d9d372bb6826bd81d3542a419d6_10485760_2048
```

这里把 MD5、文件大小和分片大小都放入 ID，目的是让“同一个文件、同一种分片规则”在重连后
仍然定位到同一项任务。`upload_id` 不使用 `session_id`，因为 TCP 重连必然会产生新的会话 ID。

服务端会校验 `upload_id` 只包含字母、数字、`_`、`-`，再用它拼接路径，避免把客户端传入的
字符串当作任意目录来访问。

目录结构改为：

```text
uploads/
  <upload_id>/
    meta.json       # 任务元数据
    data.part       # 尚未完成时的临时文件
    报告.docx        # 完成后发布的最终文件
```

`meta.json` 保存 `upload_id`、MD5、原始文件名、总大小、分片大小和完成状态。若同一目录中已有
元数据，但本次请求的 MD5、文件名、总大小或分片大小不一致，服务端返回 `UploadTaskConflict`
（1013），拒绝覆盖已有任务。

#### 2. 上传前先同步服务端进度

消息 ID：

```text
ID_SYNC_FILE_REQ = 1005
ID_SYNC_FILE_RSP = 1006
```

客户端不再直接发第一个文件分片，而是先发送同步请求：

```json
{
  "upload_id": "9e107d..._10485760_2048",
  "md5": "9e107d...",
  "name": "报告.docx",
  "total_size": 10485760,
  "chunk_size": 2048
}
```

服务端的 `HandleSyncFile` 按以下顺序处理：

1. 创建 `uploads/<upload_id>/`；第一次同步时创建 `meta.json`。
2. 若最终文件已经存在且大小等于 `total_size`，说明任务完成，返回 `completed: true`。
3. 否则读取 `data.part` 的文件大小。这个大小就是连续、已成功落盘的 `confirmed_offset`。
4. 返回同步结果。

```json
{
  "error": 0,
  "upload_id": "9e107d..._10485760_2048",
  "total_size": 10485760,
  "confirmed_offset": 4096,
  "completed": false
}
```

收到回包后，客户端调用 `file.seek(confirmed_offset)`，只读取并发送未确认的部分。若返回
`completed: true`，客户端显示“服务器已有完整文件，已秒传完成”，不再传输数据。

#### 3. 分片从 seq 改为 offset

改造后的上传分片不再依赖 `seq`、`trans_size`、`last_seq`，而是带上该分片写入的位置：

```json
{
  "upload_id": "9e107d..._10485760_2048",
  "md5": "9e107d...",
  "name": "报告.docx",
  "total_size": 10485760,
  "offset": 4096,
  "is_last": false,
  "data": "Base64..."
}
```

服务端读取 `data.part` 当前大小作为 `confirmed_offset`，并按下面的规则处理：

| 请求中的 `offset` | 含义 | 服务端行为 |
| --- | --- | --- |
| `offset == confirmed_offset` | 正常的下一片 | 追加写入，返回新的已确认偏移 |
| `offset < confirmed_offset` | 网络超时后的重复包 | 不重复写入，直接返回当前偏移 |
| `offset > confirmed_offset` | 客户端跳过了分片或进度过期 | 返回 `UploadOffsetMismatch`（1014）和期望偏移 |

这让分片请求具备幂等性：客户端没有收到回包时可以安全重试，不会把同一段数据写两次。
服务端还会校验 `offset + 解码后数据长度 <= total_size`，并要求 `is_last` 与“本片写完后
恰好达到总大小”一致，防止异常包把文件写过界。

同一个 `upload_id` 可能同时被旧连接和重连后的新连接访问。当前实现用一个进程内互斥锁保护
同步、检查文件大小、追加写入、完成重命名这一整段临界区，保证临时文件不会被并发写坏。生产
环境可进一步优化为“每个 upload_id 一把锁”，以避免不同任务之间互相等待。

#### 4. 一片一确认，而不是一次性发送全文件

客户端以前在循环内连续调用 `socket->write()`，网络断开时大量未确认分片可能仍堆在写队列中。
现在的流程是：

```text
同步进度
   ↓
读取 offset 对应的一片
   ↓
发送 ID_UPLOAD_FILE_REQ
   ↓
收到 ID_UPLOAD_FILE_RSP（confirmed_offset）
   ↓
仍处于“上传中”状态？──否──→ 停止发送
   │
  是
   ↓
发送下一片
```

客户端进度条和文字都使用服务端回包的 `confirmed_offset`，而不是本地“已经调用 write 的字节数”。
由于 `QProgressBar` 的范围是 `int`，界面内部用 0～1000 的千分比显示进度，实际字节数仍使用
`qint64`，避免 2GB 以上文件的进度范围溢出。

#### 5. “暂停上传 / 继续上传”按钮

原来的“查询续传进度”按钮已经改为状态切换按钮：

* 未开始上传时按钮禁用。
* 开始上传后显示“暂停上传”。点击后将客户端 `_upload_active` 设为 `false`，按钮文字变为
  “继续上传”。不会删除服务端的 `data.part`。
* 如果点击暂停时刚好有一片在网络中，该片仍可能得到服务端确认；但回包到达后发现
  `_upload_active == false`，客户端不会再发送下一片，因此会稳定地停在服务端确认的位置。
* 点击“继续上传”后，客户端再次发送同步请求，取得最新 `confirmed_offset`，然后从该位置继续。
  这样即使暂停发生在分片回包前，也不会重传或漏传。
* 上传完成时按钮重新禁用；重新选择文件也会清除旧任务的暂停状态。

#### 6. 完成发布和当前边界

最后一片写入成功后，服务端将 `data.part` 重命名为任务目录中的原始文件名，并在 `meta.json`
中标记 `completed: true`。因此外部读取最终文件时不会读到传输中的半成品。

本次实现中，MD5 用于生成稳定的 `upload_id` 与校验任务元数据；**服务端暂未在完成后重新计算
文件 MD5**。如果需要防御本地文件被修改、磁盘损坏或恶意客户端伪造 MD5，应在重命名前计算
`data.part` 的 SHA-256（推荐）或 MD5，与客户端声明值比较；不一致时保留 `.part` 供排查或删除
并返回校验失败。

涉及的主要代码位置：

* 客户端上传状态机：`resourse_client/mainwindow.cpp`
* 客户端协议回包解析：`resourse_client/tcpclient.cpp`
* 服务端同步、偏移校验与落盘：`server/src/LogicWorker.cpp`
* 协议消息 ID 和错误码：`server/include/const.h`、`resourse_client/global.h`





## 存在问题



### 不同客户端上传同名文件

在两个客户端上传同名文件时，会并发写同一个uploads/报告.docx



#### 按会话分目录

最简单的处理方式是按会话分目录

```
  uploads/
    session_A/
      报告.docx
    session_B/
      报告.docx
```

路径概念上变成

```
file_path / session->GetSessionId() / file_name
```

但是这样不适合断点续传，客户端重新连接会获得一个新的`session_id`，导致续传文件落在另一个目录



#### 按照上传任务标识分目录

例如`uoload_id`分目录

```
upload_id = md5 + "_" + total_size + "_" + chunk_size;
```

这样还可以用于断点续传查找文件进度

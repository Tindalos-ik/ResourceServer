# 文件上传



## 设计思路

文件传输必须满足以下几个条件

* 限制文件大小(不超过4G)

* 长连接传输(效率高，支持大文件)

  > 文件传输不允许任何数据丢失，并且需要保证数据包到达顺序，而且TCP有流量控制和拥塞控制，更适合文件传输

* 客户端和服务器都知道传输进度，以保证支持断点续传(后续实现)



先实现单线程处理版本，再实现多线程的



## 客户端

客户端由`TcpClient`来进行数据的发送

```cpp
//发送数据槽函数
void TcpClient::slot_send_msg(quint16 id, QByteArray body)
{
    //如果连接异常则直接返回
    if(_socket->state() != QAbstractSocket::ConnectedState){
        emit sig_net_error(QString("断开连接无法发送"));
        return;
    }

    //获取body的长度
    quint32 bodyLength = body.size();

    //创建字节数组
    QByteArray data;
    //绑定字节数组
    QDataStream stream(&data, QIODevice::WriteOnly);
    //设置大端模式
    stream.setByteOrder(QDataStream::BigEndian);
    //写入ID
    stream << id;
    //写入长度
    stream << bodyLength;
    //写入包体
    data.append(body);

    //发送消息
     _socket->write(data);
}
```

发送格式`id + bodylength + 文件流数据`

bodylength是4个字节，所以文件最大是4G

由其他地方发送信号实现数据发送

```
 //连接 发送数据信号和槽函数
 connect(this, &TcpClient::sig_send_msg, this, &TcpClient::slot_send_msg);
```

客户端选择文件后，点击发送会把文件切分成固定大小的报文发送

```cpp
void MainWindow::on_uploadButton_clicked()
{
    // 设置按钮不可点
    ui->uploadButton->setEnabled(false);
    QFile file(_file_path);
    if(!file.open(QIODevice::ReadOnly)){
        qWarning() << "Could not open file:" << file.errorString();
        return;
    }
    
    QFileInfo fileInfo(_file_path); // 用完整路径构造
    int total_size = fileInfo.size();
    int last_seq = 0;
    // 计算分块大小
    if(total_size % MAX_FILE_LEN){
        last_seq = total_size  / MAX_FILE_LEN + 1;
    }else{
        last_seq = total_size / MAX_FILE_LEN;
    }
    
    // 读取文件内容进行发送
    QByteArray buffer;
    int seq = 0;
    while(!file.atEnd()){
        // 每次读取2048字节，分块传输
        buffer = file.read(MAX_FILE_LEN);
        QJsonObject jsonObj;
        // 将文件内容转换位Base64编码
        QString base64Data = buffer.toBase64();
        seq++;
        jsonObj["md5"] = _file_md5;
        jsonObj["name"] = fileInfo.fileName(); //提取出文件名
        jsonObj["seq"] = seq; // 报文序列号
        jsonObj["trans_size"] = buffer.size() + (seq-1)*MAX_FILE_LEN; //已经传输的大小
        jsonObj["total_size"] = total_size;
        if(buffer.size() < MAX_FILE_LEN){
            jsonObj["last"] = 1;
        }else{
            jsonObj["last"] = 0;
        }
        jsonObj["data"] = base64Data;
        jsonObj["last_seq"] = last_seq;
        QJsonDocument doc(jsonObj);
        auto send_data = doc.toJson();
        emit TcpClient::GetInstance()->sig_send_msg(ID_UPLOAD_FILE_REQ, send_data);
    }
}
```

```cpp
void LogicSystem::HandleUploadFile(std::shared_ptr<CSession> session, const short &msg_id, const std::string &msg_data)
{
    Json::CharReaderBuilder reader;
    Json::Value root;
    std::istringstream ss(msg_data);
    std::string errs;
    bool parse_success = Json::parseFromStream(reader, ss, &root, &errs);
    if (!parse_success) {
        std::cout << "Failed to parse JSON data" << std::endl;
        std::cout << errs << std::endl;
        return;
    }

    Json::Value rtvalue;
    Defer defer([this, session, &rtvalue]() {
        std::string return_str = rtvalue.toStyledString();
        session->Send(return_str, ID_UPLOAD_FILE_RSP);
    });

    std::string data = root["data"].asString();
    // 客户端上传的是 Base64 文本，保存前必须还原为原始二进制字节。
    std::string decoded_data;
    if (!Base64Decode(data, decoded_data)) {
        std::cout << "Failed to decode Base64 data" << std::endl;
        rtvalue["error"] = ErrorCodes::Error_Json;
        return;
    }

    auto seq = root["seq"].asInt();
    auto name = root["name"].asString();
    auto total_size = root["total_size"].asInt();
    auto trans_size = root["trans_size"].asInt();
    auto file_path = ConfigMgr::Inst().GetFilePath();
    // JSON 中的中文文件名为 UTF-8，u8path 可避免 Windows 按本地代码页解释而乱码。
    // filename() 只保留名称，防止客户端传入 "../" 等路径越界写文件。
    auto file_name = std::filesystem::u8path(name).filename();
    if (file_name.empty()) {
        std::cout << "Invalid file name" << std::endl;
        rtvalue["error"] = ErrorCodes::Error_Json;
        return;
    }
    auto file_path_str = file_path / file_name;
    std::cout << "file_path: " << file_path_str << std::endl;
    std::ofstream outfile;
    if(seq == 1){
        // 第一个包需要创建
        // 打开文件，如果存在则清空，不存在则创建
        outfile.open(file_path_str, std::ios::binary | std::ios::trunc);
    }else{
        // 保存为文件
        outfile.open(file_path_str, std::ios::binary | std::ios::app);
    }
    if(!outfile){
        std::cout << "Failed to open file" << std::endl;
        return;
    }
    outfile.write(decoded_data.data(), decoded_data.size());
    if(!outfile){
        std::cout << "Failed to write file" << std::endl;
        return;
    }
    outfile.close();
    std::cout << "Write file success" << name << std::endl;

    rtvalue["error"] = ErrorCodes::Success;
    rtvalue["seq"] = seq;
    rtvalue["name"] = name;
    rtvalue["total_size"] = total_size;
    rtvalue["trans_size"] = trans_size;
    }
```

## 多线程逻辑服务器

多线程逻辑服务器主要是为了缓解单线程接收数据造成的瓶颈，因为单线程接收数据，就会影响其他线程接收数据，所以考虑引入线程池处理



划分多线程的几种思路

* 按照任务划分，将不同的任务投递给不同的线程

  也就是不要让IO线程既收包，又解码，又写文件，可以分为

  * 网络线程：接收tcp数据，拆包

  * 解析线程：解析json
  * 文件线程：创建目录，写入文件分片
  * 网络线程：文件写成功后发送上传回包

  这一磁盘写入慢时，不会阻塞其他客户端继续收包

* 按照线程数轮询处理

  也就是现在 `AsioIOServicePool`的思路

* 按照递归的方式划分

  递归：也就是大任务拆成小任务

  例如一个大文件范围：

  ```
    [0, 文件末尾]
            ↓
    拆成 [0, mid] 和 [mid + 1, 文件末尾]
            ↓
    继续拆分，直到每块不超过设定大小
            ↓
    每一块成为一个可投递任务
  ```

现在客户端已经按照2048字节上传分片，不需要服务器再拆，服务器可以直接将每个收到的分片作为一个任务投递即可，所以考虑第二种，服务器通过`iocontext`池接收数据，将接收的数据投递到线程池

关键在于，同一文件的分片要保证顺序写入

有几种处理思路



### 按照文件划分

```
  文件 A 的所有分片 → 固定文件线程 0
  文件 B 的所有分片 → 固定文件线程 1
  文件 C 的所有分片 → 固定文件线程 2
```

用文件唯一标识计算对应的固定线程，比如MD5

在固定现在内部按队列顺序写入，从而可以安全的使用`std:ios::app`

还需要保留`seq`校验，因为分片可能重传，跨连接上传

```
  struct UploadState {
      int next_seq = 1;                     // 下一个允许写入的分片
      std::map<int, FileChunk> pending;     // 先到但尚不能写的分片
      std::mutex mutex;
  };
```

写入逻辑

```cpp
 void HandleChunk(const FileChunk& chunk)
  {
      std::lock_guard<std::mutex> lock(state.mutex);

      if (chunk.seq < state.next_seq) {
          return; // 已写过：重传包，忽略或直接回成功
      }

      state.pending[chunk.seq] = chunk;

      // 只有连续分片才允许追加写入
      while (state.pending.count(state.next_seq)) {
          auto& current = state.pending[state.next_seq];
          AppendToFile(current.data);

          state.pending.erase(state.next_seq);
          ++state.next_seq;
      }
  }
```

但是呢，这一有个弊端，如果文件很大，需要等待重组完成才能组合成一个统一的包，这个时间很长

当然也可以缓存这些数据，每次收到后排序组合，但是比较麻烦



### 按照客户端划分

另一种思路，按照不同的客户端区分

```
  客户端 A 的所有请求 → 工作线程 0
  客户端 B 的所有请求 → 工作线程 1
  客户端 C 的所有请求 → 工作线程 2
```

只要同一客户端的任务在同一条单消费者队列中执行，TCP接收顺序就是业务处理顺序，分片就可以继续使用`std::ios::app`追加写入

可以使用`session_id`计算线程索引

```
 std::size_t GetWorkerIndex(const std::string& session_id)
  {
      return std::hash<std::string>{}(session_id) % _workers.size();
  }
```

投递的时候

```
auto index = GetWorkerIndex(session->GetSessionId());

_workers[index]->Post([session, msg_data]() {
	HandleUploadFile(session, msg_data);
});
```

这样，同一连接发送的seq =  1, 2, 3 ... 会进入同一工作线程

一个客户端的多个请求也会保持先后顺序，不同客户端可以并行上传

当前`CServer`已经是这样的写法

```
  void CServer::StartAccept() {
      auto& io_context = AsioIOServicePool::GetInstance()->GetIOService();

      auto new_session =
          std::make_shared<CSession>(io_context, this);

      _acceptor.async_accept(new_session->GetSocket(), ...);
  }
```

CSession 的 socket 在创建时就绑定了本次轮询得到的 io_context

```
  客户端 A 建连 → 分配 IO 线程 0
  客户端 A 的分片 1、2、3 → 都由线程 0 的 CSession 处理

  客户端 B 建连 → 分配 IO 线程 1
  客户端 B 的分片 1、2、3 → 都由线程 1 的 CSession 处理
```



但是，当前逻辑处理是单线程，所有客户端业务串行执行

```
  客户端 A 上传分片 1
  客户端 B 上传分片 1
  客户端 A 上传分片 2
```

我们完成一下多线程逻辑处理，一个客户端用一个`logic_worker`，于是

* 同一个客户端仍按顺序处理
* 不同客户端可以并行写不同文件
* IO线程不被磁盘写入阻塞



### 处理逻辑

我们先在逻辑层这里做一下解耦合，将logic线程扩充为多个，按照`sessionid`将不同的客户端连接分配给不同的线程处理

让`LogicSystem`作为业务调度中心

```
创建和管理多个LogicWorker
客户端连接建立时候，为该客户端分配一个LogicWorker
收到CSession投递的LogicNode后，根据客户但所属Worker转发任务
连接断开后，删除session_id -> worker 的映射
```

这样同一客户端永远由同一个LogicWorker顺序执行，不同客户端会被轮询分到不同的worker并行处理

```
class LogicSystem : public Singleton<LogicSystem> {
    friend class Singleton<LogicSystem>;
public:
    ~LogicSystem();
    // 新客户端连接时轮询绑定 session_id 到 worker
    void BindSession(const std::string& session_id);
    // 根据index将消息给到对应的worker线程
    void PostMsgToQue(std::shared_ptr<LogicNode> msg);
private:
    LogicSystem();
    std::vector<std::shared_ptr<LogicWorker>> _workers; // 工作线程池
    std::unordered_map<std::string, std::size_t> _session_worker_map; // session到worker的映射
    std::atomic<std::size_t> _next_worker; // 下一个worker，轮询处理
};
```

## 断点续传

断点续传通过借助MD5(或更常见的SHA-256)来确认已传部分和最终文件是否正确

* 断点续传：上传/下载中断后，从已完成的位置继续传，核心是记录偏移量，分片编号和已完成分片

* MD5：文件内容的摘要/指纹，用于识别内容和校验完整性

  > MD5是一种哈希算法，全程 Message Digest Algorithm5 消息摘要算法5
  >
  > 它会把任意大小的数据，例如一个文件，一段文本，计算成固定长度的32位十六进制字符串
  >
  > 常用于文件完整性校验，文件去重，上传任务标识

* SHA-256，和MD5类似，不过它是生成64位十六进制字符串



常见组合方式

* 秒传/去重

  客户端先计算整个文件的MD5并询问服务端是否已有该文件，已有无需上传，没有开始分片上传

* 续传定位

  客户端带上MD5作为上传任务标识，请求服务端查询已上传的分片或偏移量，然后仅补传缺失部分

* 完整性校验

  上传完成后，服务端计算合并后文件的MD5，与客户端提供的MD5比较

* 分片校验

  也可每个分片带一个MD5，服务器逐片验证，避免某个分片传输损坏后仍被合并
